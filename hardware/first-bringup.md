# 首轮上板：先看见真实摄像头画面

配套：[空白验收记录](first-bringup-record.md)。适用两名零基础队员、两台 Windows、共用一块板。首轮检查点为 2026-10-02 至 2026-10-04，最终目标为 2026-11-04；不因赶日期跳过核验。

**当前只知道用户报告板、摄像头、供电/下载线、显示器到货。实物型号、附件兼容性、FPC 方向和功能都未验证。本指南没有执行过接线、扫描、下载或编译。** 文档中的工程目标不是实物识别结果。

## 0. 两个人怎样开始

- 操作员只操作接板的那台电脑；记录员在另一台电脑读步骤、填写记录并核对“本次只改一个变量”。同一时段不让两个下载窗口或两台电脑争用板卡。
- 第一次先做到第 1 步，把照片与问题交给主对话；**用户明确确认接线和扫描后**才能进入第 2 步。下载前还要确认本次 bit 与“临时配置”操作。
- 先不接 DFPlayer、扬声器和其他外设。准备无金属杂物的桌面，不在带电状态触碰裸露导体或调整接线。
- 有异味、异常发热、冒烟或供电反复掉电：立即停止并安全切断供电，不反复试上电。任何型号、接口或手册不对应：停下拍照，不靠“插得进去”判断兼容。
- **FPC 只允许完全断电后插拔；禁止热插拔。** 断电须包括可能由 USB/下载器回供的电源，按对应实物手册确认已无供电；不把熄灯当成唯一证明。
- Flash 擦写/固化、下载器固件更新、驱动替换和 Windows 安全设置变化都是独立操作，必须另获用户确认。本指南不要求关闭任何安全保护，也不提供这类绕过步骤。

记录员先打开验收表。现场结果只写实际观察：未执行、失败、证据不足均不能记为通过。主对话审核前不宣称达到 `m1-bringup`。

## 1. 完全断电，先核对实物与资料

1. 暂不连接电源、USB 下载器或 FPC；若已经连接，请先按实物手册安全断电。保留当前接法照片，**不要在带电时拆线取景**。
2. 拍六组清晰照片：板正反面及版本丝印、FPGA 字样、摄像头正反面、FPC 两端触点与转接件、板与摄像头插座近照、电源铭牌与输出插头。补拍下载器/线缆标签及显示器型号。对外共享前遮住地址、订单、序列号等无关个人信息，不遮挡核验所需型号参数。
3. 打开本机资料入口中对应板版本的手册。记录**文件名、版本、页码**，逐项抄入验收表：允许的供电方式、额定电压/电流要求、接口与极性、电源开关/选择设置、能否与 USB 同时供电。拿电源铭牌逐项比对；本文不替实物给出电压、极性或跳线位置。
4. 对照摄像头模块资料与该板接口资料，核对模块型号、排线/转接线类型、两端触点朝向、插座锁扣及线序兼容性。**不能仅凭针数相同、排线蓝面或照片视角推定方向。** 无匹配接线图时提交近照请主对话核对，不插入试错。
5. 核对显示器说明支持 `1280×720 @ 60 Hz`，确认实际 HDMI 输入口。记录线缆、光照、背景、相机摆放，后续测试保持不变。
6. 记录员复述连接方案，标出尚不确定的项。用户确认方案及“连接并扫描”的范围后，在表中记下确认人和时间，再继续；尚未确认就停在这里。

**本步交付：**照片、手册页码、核对表和用户确认。只有“收到货”不足以放行。

## 2. 按确认方案连接，只做下载器与器件识别

1. 按刚核对的实物手册顺序连接摄像头/FPC、HDMI、下载器和电源；FPC 操作始终在完全断电下进行，再锁好锁扣。不要尝试未知引脚、供电口或跳线。选择显示器对应 HDMI 输入。
2. 在 Windows 设备管理器记录下载器设备名、设备状态、硬件 ID、驱动供应商和版本；截图保留完整错误码。另记录 Windows 版本及 TD “关于”页面。项目要求 TD 6.2.1，不用更高版本碰运气。
3. 如果驱动尚未就绪，停下报错，由主对话安排单独的驱动核验；不要自动运行驱动替换工具。下列扫描入口只适用于核对为相应 AL-LINK-FT 方案、且已有正常驱动的情况。
4. 打开 TD 配套下载窗口，参考本机 `PH1P35烧写程序的使用方法.pdf` 第 2—3 页：进入 `AL-LINK-FT(Local Host)`，刷新，然后 `Apply and Close`。该资料记录本地端口默认 5555，**不要因此改已有配置**；窗口不一致时先截图核对。首次未显示器件可按文档再刷新一次并稍等，不能靠反复改驱动/端口试错。
5. 截图记录实际器件名/ID。工程候选目标为 `PH1P35MDG324`；须同时与板上标识、资料对应。扫描成功仅证明通信和识别，**不证明摄像头、DDR 或 HDMI 正常**。

**放行条件：**设备状态正常、目标型号相符、用户/记录员核对截图。未知器件或型号不符即停，不强行选择近似型号；此步不点击下载、擦除或 Flash 操作。

## 3. 官方候选预编译 bit：先临时下载看画面

1. 使用后文“本机路径与来源”中的**官方候选**普通 bit，而不是工作副本同名文件。核对资料包来源、板版本和摄像头兼容性，计算本次 SHA-256 并填写记录。仅放在 `Data/` 目录不构成官方真实性认证；资料来源不明就先补证据。
2. 在下载窗口选择目标 FPGA 的**易失配置/临时下载**模式；界面可能标为 RAM、SRAM 或 FPGA 配置，必须按实际工具/手册确认不是 SPI/Flash 编程。菜单含义不清时把窗口截图给主对话，不能只凭按钮名猜。记录员复核完整 bit 路径、哈希、器件和模式，用户确认本次下载后才开始。
3. 保存下载开始/结束时间、实际 GUI 步骤或命令、状态和错误信息。下载工具显示成功之后，再看显示器：打开显示器“信号信息”记录分辨率与刷新率；把有颜色的物体缓慢移进、移出镜头，确认屏幕随之变化，而不是静止图、测试彩条或其他输入源。
4. 观察至少 2 分钟，记录是否黑屏、偏色、条纹、错位、卡住或掉信号。保存含实物动作与屏幕反应的短视频；显示器若不能报告模式，就把“720p60 实测确认”保留待验证，不凭肉眼填写 60 Hz。

**放行条件：**本次临时下载有记录、可看到随实物运动的摄像头画面、模式有证据且短测无异常。失败留在此步排查，不同时更换 bit、排线、供电和显示器。官方候选一旦实测可用，记住其精确来源/哈希，保持原文件不变，作为下一步回退点。

1. 将当前工作副本 `.al`、实际引用源码/IP/约束的版本清单及哈希交给主对话留证。记录其 Git commit 和工作树差异；若工程未纳入 Git，就写明未版本化，并保存输入文件哈希清单、官方来源和已知修改说明。单独一个顶层哈希不能代表全部输入。构建期间不再改这些输入。
2. 在 TD 6.2.1 打开后文工作副本的 `td_project/camera_to_dsi_display.al`，核对工程完整路径、顶层 `design_top_wrapper`、目标 `PH1P35MDG324`。检查工程树中源码、IP、引脚约束与时序约束引用无缺失；不新建空工程、不打开 `Data/` 中的工程进行编译。
3. 用当前 TD 界面执行综合、实现/布局布线和 bit 生成；记录实际菜单操作、开始/结束时间及工具版本。同台电脑只开一个 TD 构建。出现缺工具、License 或引用错误，记录后停止，不通过改目标器件或升级版本绕过。
4. 查看本次综合/实现日志及布线后时序报告：流程是否真正结束、是否生成 bit、有无负余量、未覆盖/未约束路径及关键告警。把报告与告警交给主对话审核。新 bit 的存在或 GUI 绿色图标不能替代报告审查；历史 95.64% 覆盖率也不是完整审查。
5. 从**本次运行日志指明的输出**定位 bit。常见位置是工作副本 `phy_1` 普通 bit，但不得仅凭此路径已有文件就判定新构建成功；核对生成时间、大小、日志和 SHA-256，把构建前/后值都记下来。若哈希未变，仍须有本次完整构建证据；若与官方不同，也不能仅凭差异判错。
6. 主对话核对来源与报告后，按第 3 步重新确认本次临时下载，使用本次新 bit 重做画面短测。记录自编译和官方候选的结果差异。失败时先保留现场，确认后临时重载已验证的官方候选，其他接线和环境不变，以区分镜像问题与硬件问题。

**放行条件：**有本次完整构建/报告审核、输入来源和产物哈希，且新 bit 上板短测通过。没有新构建证据时只能说“历史工作副本 bit”，不能说“今天重编译通过”。

## 5. 固定同一个镜像，稳定 30 分钟与恢复

1. 优先对第 4 步通过短测的新 bit 做长测，记录其完整路径和哈希；若仅官方候选能运行，可以对其测试，但自编译项仍待验证。测试期间不换镜像、不动接线。
2. 记录开始和结束的带时区时间，持续观察至少 30 分钟，在 0、5、15、30 分钟留画面记录。每个观察点把物体移入移出确认非冻结；记录全部异常及出现时刻，连续录像或观察日志补足两个端点截图不能证明的过程。
3. 任何花屏、错位、卡住、掉信号都记失败，不把修好后的时间拼接成连续 30 分钟。问题修复后以新轮次从零计时；原失败记录保留。
4. 长测完成后单独做恢复：记录当前 bit，用户确认后按手册完全断电，保持已确认接线不变，再按手册上电、重新扫描并**再次临时下载同一哈希的 bit**，检查画面恢复、记录恢复耗时。临时配置通常断电丢失，且板上既有 Flash 内容未知；上电显示别的程序或无原画面不能直接认定恢复失败，也不能据此声称冷启动验收通过。
5. 首次恢复不必拆 FPC。确需重接时，在用户另行确认后完全断电、排除 USB/下载器回供，再按已核对方向重接并锁紧，之后上电、扫描、重新临时下载同一镜像。**禁止带电插拔 FPC，也不能把复位当作断电。** 该可选测试未做就记“未执行/待验证”，不填通过。

**本轮完成条件：**照片与授权齐全、官方/自编译来源分清、本次构建已审核、真实画面和模式有证据、连续 30 分钟与断电重载恢复有记录。Flash 固化、断电自动运行、2 小时整机稳定、识别准确率均不属于此次通过结论。

## 6. 失败时只沿一个层级往下查

| 顺序 | 先收集什么 | 一次只核查一项 | 何时停下交给主对话 |
|---|---|---|---|
| 供电 | 实物全景、电源铭牌、手册页码、上电现象/时间 | 对照供电要求；不盲试电压，不让新手带电探针测量 | 不符、无法确认极性或异常发热立即停止 |
| 下载器 | Windows 设备状态/ID/驱动、扫描窗口、完整错误码 | 确认正确工具与目标；重试仅按已确认手册步骤 | 缺驱动、型号不符、需替换驱动/固件时先申请单独核验 |
| bit 来源 | 实际选择的绝对路径、SHA-256、工程/包来源、日志 | 查是否选错同名文件、目标/临时模式是否一致 | 来源或模式不清楚，不再点下载 |
| 摄像头 / HDMI | 下载结果、屏幕信号信息、场景视频、FPC/接口照片 | 保持同一 bit，先核对 HDMI 输入；涉及改线先断电并获确认 | 仍无画面时提交现象，不边换线边换工程 |

每条失败记录写“时间、原状态、唯一变更、实际结果、证据、是否恢复”。不要删除失败日志或用后一次成功覆盖。先前已验证的 bit 只在确认后用于临时回退，不为了回退擦写 Flash。

## 8. 给队友和主对话的最小交接包

- 保持[验收记录模板](first-bringup-record.md)空白；实际上板由 `env-bringup` 执行，在其获授权的 `evidence/env-bringup/runs/<run-id>/` 保存填写版及运行证据，`run-id` 用 `YYYYMMDD-HHmmss-operator` 形式的 ASCII 名称。`runs/` 按集成后的 `.gitignore` 作为本地运行产物，不随源码提交；由执行者在 `evidence/env-bringup/` 的非忽略清单中登记相对路径、双方可访问链接及 SHA-256。指南编制/验证证据仍归 `evidence/bringup-kit/`。该运行目录由实际执行时建立，本次未创建硬件证据。
- 在作品仓库根运行 `git rev-parse HEAD` 记录协作文档版本；另记工作副本的实际源码身份，两者不能混用。照片、记录、清单通过仓库相对路径交接，不把本机 `E:` 路径当作队友也能打开的证据。
- 图片用 `board-front.jpg`、`camera-front.jpg` 等 ASCII 名称。大视频/镜像不直接塞进 Git，清单记相对证据路径或双方可访问的私有链接、文件大小、SHA-256；队友实际验证能读取。记录不上传 License、安装包或未脱敏的订单。
- 每轮带上：来源/哈希、执行人与时间、工具版本、实际步骤、失败原始记录、30 分钟日志、恢复结果和待验证项。只写“PASS”或给本机截图路径不算交接完成。
- 有文件变化后，由执行对话按所在机器的共享根规则登记独立 JSON，运行该机器主库的 `tools/update-workspace-index.ps1` 与 `-Check`。Git 提交只加本任务文件，PR 和主干审核由主对话负责；本小任务不推送、不合并。
