# 测试计划

## 1. 测试层级

1. 模块仿真：纯组合逻辑、时序逻辑和接口协议。
2. 集成仿真：使用录制或生成的图像验证检测结果。
3. 上板短测：单个模块在真实视频流中运行。
4. 系统长测：完整镜像连续运行。
5. 演示验收：按现场流程完成探索和问答。

## 2. 测试环境记录

每次测试记录：

- 日期、测试人、分支和提交号。
- TD、ModelSim、驱动和操作系统版本。
- 开发板、摄像头、显示器、供电和接线。
- 光照、背景、相机高度和物体位置。
- 测试命令、输入素材和原始输出。

## 4. 识别采样规则

- 每类积木至少 20 次，覆盖中心、轻微左偏、轻微右偏和略微旋转。
- 每张卡片至少 20 次，覆盖中心、轻微左偏和轻微右偏。
- 每次先移出目标，等待 2 秒，再放入。
- 主观判断直接看 OSD 和语音结果。
- 记录首次稳定结果和是否在 3 秒内。

计算公式：

```text
正确率 = 正确次数 / 总次数 * 100%
```

达不到阈值时，优先调整相机距离、灯光、阈值和模板，不先增加模型复杂度。

## 5. 回归测试

每个合并到 `main` 的模块至少执行：

- 受影响模块仿真。
- 原始视频显示短测。
- 本模块验收。
- 最近一个已通过系统的关键回归。

最终版本执行全部必测项目。

## 6. 证据要求

- 文件检查、脚本回归、模块仿真、工程实现、上板与发布分层记录；GitHub Actions 不替代 TD、ModelSim 或板卡验收。
- 软件报告记录被测 HEAD、工具版本、完整命令、退出码和原始日志哈希。源码变化后旧报告失效，不以 PASS 文本或零退出单独判通过。
- 先提交源码和说明，再测试；运行产物放独立 runs 目录，通过 PR 附件或可访问链接交接，不为提交报告改变被测 HEAD。
- 故障注入应被检查器检测为失败；“负向测试按预期失败”只能证明检查器有效，不能证明 DUT 正常。
- 历史 lab1 的 95.64% STA 覆盖和正 WNS 不代表全部约束/CDC 已审核；上板前核对实际源码、工程清单与镜像。
- 烧录、固化、接线、系统安全设置变更须事前用户确认；首次上板记录从 hardware/first-bringup-record.md 创建任务副本。

- 照片和截图必须能看清屏幕内容、接线和环境。
- 视频要包含失败到恢复的过程，不只保留成功片段。
- 表格记录原始次数，不只写百分比。
- 大型视频放 `evidence/video/`，仓库只提交清单和校验值。
